## Executive Summary

Release signing + custom-AVB-key + bootloader locking is **GO** for GuardTalkOS. The upstream AOSP/GrapheneOS build already contains a complete, functional signing pipeline, and a full set of release keys + AVB key already exists at `keys/tokay/` (encrypted PKCS#8 with a passphrase). The signing pipeline `releases/2026061500/release-tokay-2026061500/script/generate-release.sh` is the GrapheneOS-derived reference and is directly reusable. The only missing piece is wiring a GuardTalkOS-owned signing flow that *does not* use `--disable-verification` (the current dev flash path) and a bootloader-lock procedure.

**CRITICAL CAVEAT (Law 4 — Security First):** Loss of the AVB private key (`avb.pem`) after the bootloader is locked with the custom key is a **PERMANENT BRICK** of the device — there is no recovery path. Key custody MUST be solved (offline backup / HSM) before locking.

**Key correction to the brief:** The brief states "No signing/AVB/lock infra exists in `vendor/guardtalk/`." That is only partially accurate. While `vendor/guardtalk/` itself contains only dev-flash scripts, the repo root contains:
- `keys/tokay/` — a full release key set + `avb.pem` + `avb_pkmd.bin` (encrypted)
- `releases/2026061500/` — a complete GrapheneOS-style release pipeline (`generate-release.sh`, `decrypt-keys`, `generate-factory-images-common.sh`)
- An already-built signed release `tokay-factory-2026061500.zip`

These are GrapheneOS-derived assets inherited from the manifest, NOT GuardTalkOS-owned. Section 1 documents this in detail.

1. They are GrapheneOS-derived release keys inherited from the GrapheneOS build manifest (the `releases/.../script/` tree is the GrapheneOS release tooling). 2. **GuardTalkOS should generate its OWN fresh key set** rather than reuse these. The existing keys are fine to reuse ONLY if their provenance is fully trusted and their passphrase is known. Reusing GrapheneOS keys would mean any GrapheneOS-signed image (if such exists with these keys) would also pass AVB on a GuardTalkOS-locked device — defeating the purpose of a GuardTalkOS-specific root of trust.

**Custody model recommendation (Law 4, Law 11 reversibility):**
- Generate keys on a dedicated **offline, air-gapped machine** (no network, no Bluetooth — recall BT is excised anyway).
- Encrypt each `.pk8` with a strong passphrase via `make_key`'s scrypt mode.
- Store the encrypted keys in **3 geographically separated encrypted backups** (e.g., LUKS-encrypted USB drives in 3 safes).
- The signing host decrypts to tmpfs (`/dev/shm`) at signing time, signs, and the `trap` ensures the plaintext keys never hit disk. This is exactly the pattern in `releases/.../script/generate-release.sh:18-21`.
- For higher assurance, use an HSM or a YubiKey with `--signing_helper` (the `sign_target_files_apks.py` `--avb_*_extra_args` flags at lines 108-123 support a custom signing helper).

**Keys must NOT be committed to the repo.** Verify `.gitignore` covers `keys/`. The existing `keys/tokay/.git` is a symlink to `../../.repo/projects/vendor/guardtalk.git` — wait, that was `vendor/guardtalk/.git`, not `keys/`. Let me note: `keys/` does not appear to be a repo project (no `.git` inside), but it IS in the worktree. **Recommendation: confirm `keys/` is in `.gitignore` or is a repo-local untracked directory; if tracked, remove from git history.**

### 1d. Irreversibility — AVB key loss = PERMANENT BRICK

**VERIFY (per the brief's request):** What happens if the AVB private key is lost after the bootloader is locked with the custom key?

**Finding:** Once the bootloader is locked with a custom AVB key flashed to `avb_custom_key`, the bootloader will ONLY boot images whose vbmeta chain is signed by that key. To reflash, you must either:
1. Unlock the bootloader (`fastboot flashing unlock`), which **wipes userdata** and requires `unlock_ability=1`. But on Pixel 9 with custom-key lock, the unlock itself requires the device to accept the unlock — which it does, BUT this is where the brick risk arises.
2. Re-sign images with the AVB key — impossible if the key is lost.

**Critical nuance on Pixel 9 (tokay):** The `flash-from-remote.sh:188-198` comment in `vendor/guardtalk/scripts/` explicitly states:

```188:198:vendor/guardtalk/scripts/flash-from-remote.sh
# AVB key: build uses test keys (testkey_rsa4096.pem).
# Pixel 9 has secure-boot: PRODUCTION and no avb_custom_key partition.
# Even if avb_custom_key flashes successfully, the root vbmeta.img has Flags: 0
# (verification ENABLED) with inline hash trees for ALL partitions. If the root
# vbmeta is flashed WITHOUT --disable-verification, the bootloader will attempt
# dm-verity hash tree verification on the modified partitions and fail with
# "dm-verity device corrupted" (reboot mode 0x50).
```

**This comment is about the DEV/test-key flow** and claims "Pixel 9 has secure-boot: PRODUCTION and no avb_custom_key partition." This appears to **contradict** the GrapheneOS factory script at `releases/.../device/common/generate-factory-images-common.sh:226-232`, which DOES flash `avb_custom_key` for tokay (line 61 lists `tokay` as supported). The GrapheneOS flow is the authoritative one — the `avb_custom_key` partition DOES exist on Pixel 9 (GrapheneOS relies on it for every release). The dev-script comment likely reflects an early misunderstanding or a device-state quirk (the partition may only be writable when the bootloader is unlocked).

**Confirmed brick condition:** If you lock the bootloader with your custom AVB key and then lose the key:
- You CANNOT sign new images to flash.
- `fastboot flashing unlock` on Pixel 9 requires `get_unlock_ability=1` (set in Settings → Developer Options → OEM Unlocking) and wipes userdata. The unlock DOES work with a custom-key-locked bootloader (it reverts the device to unlocked/Google-key state) — BUT this requires the user to have left OEM Unlocking enabled. If OEM Unlocking is disabled after lock (the secure default), the device CANNOT be unlocked, and without the AVB key you cannot boot any image. **PERMANENT BRICK.**

**Recommendation:** Before locking, decide whether to leave OEM Unlocking enabled (recovery path at the cost of physical-access attack surface) or disable it (stronger security, no recovery on key loss). For GuardTalkOS operator devices, recommend: leave OEM Unlocking enabled until custody is proven, then disable.

## 2. Signing Pipeline

### 2a. sign_target_files_apks — exact invocation

The reference invocation is at `releases/2026061500/release-tokay-2026061500/script/generate-release.sh:74-171`. Key structure:

```bash
# Decrypt keys to tmpfs first (generate-release.sh:18-21)
KEY_DIR=$(mktemp -d /dev/shm/generate-release.XXXXXX)
trap "rm -rf \"$KEY_DIR\" && rm -f \"$PWD/$RELEASE_OUT/keys\"" EXIT
cp "$PERSISTENT_KEY_DIR"/* "$KEY_DIR"
script/decrypt-keys "$KEY_DIR"

# Sign (generate-release.sh:74-171)
sign_target_files_apks \
    -o \                                              # --replace_ota_keys
    -d "$KEY_DIR" \                                   # --default_key_mappings <dir>
    --avb_vbmeta_key "$KEY_DIR/avb.pem" \             # AVB root vbmeta key
    --avb_vbmeta_algorithm SHA256_RSA4096 \
    --extra_apks <apex.apex>="$KEY_DIR/releasekey" \  # per-APEX container key (repeated ~50x)
    --extra_apex_payload_key <apex.apex>="$KEY_DIR/avb.pem" \  # per-APEX payload key (repeated ~50x)
    $TARGET_FILES_INPUT $TARGET_FILES                 # input.zip output.zip
```

**Flags explained (verified against `build/make/tools/releasetools/sign_target_files_apks.py`):**
- `-o` / `--replace_ota_keys` (line 1692-1693): replaces `META/otakeys.txt` + `*/otacerts.zip` with the new release key's public cert. Required for OTA verification to use the new key.
- `-d <dir>` / `--default_key_mappings` (line 1432-1448, the `BuildKeyMap` function): maps the 10 dev keys → release keys in `<dir>/`. This is the master key swap.
- `--avb_vbmeta_key` / `--avb_vbmeta_algorithm` (lines 1713-1716): replaces the AVB signing key for the root vbmeta partition via `ReplaceAvbSigningKeys()` (line 1370-1401). The key is written into `misc_info['avb_vbmeta_key_path']` and `misc_info['avb_vbmeta_algorithm']`.
- `--extra_apks <name>=<key>` (line 1673-1677): overrides the container key for specific APEXes. The generate-release.sh lists ~50 APEXes explicitly to force them all to `releasekey`.
- `--extra_apex_payload_key <name>=<key>`: overrides the AVB payload key for APEXes — set to `avb.pem` for all, so APEX payloads are AVB-signed with the same key as vbmeta.

**`misc_info.txt` key mapping:** `ReplaceAvbSigningKeys()` (line 1383-1384) writes:
```
avb_vbmeta_algorithm=SHA256_RSA4096
avb_vbmeta_key_path=<path to avb.pem>
```
into `META/misc_info.txt` of the signed target-files (via `ReplaceMiscInfoTxt` at line 1355-1367). The build system reads these during `add_img_to_target_files` to re-stamp the vbmeta images.

**Input:** `tokay-target_files.zip` from `m dist` (or `m target-files-package`).
**Output:** signed `tokay-target_files.zip`, then fed to `ota_from_target_files` and `img_from_target_files`.

## 3. Bootloader Locking with Custom Key

### 3a. The exact sequence for tokay (Pixel 9)

Derived from the GrapheneOS factory `flash-all.sh` template (`releases/.../device/common/generate-factory-images-common.sh`) and the fastboot command surface in `system/core/fastboot/fastboot.cpp:570-575`:

```bash
# 0. PREREQUISITE: enable OEM unlocking on the device (Settings → Developer Options → OEM Unlocking)
#    This sets flashing get_unlock_ability = 1.

# 1. Flash bootloader + radio (slot A and B)
fastboot flash --slot=other bootloader bootloader-tokay-<ver>.img
fastboot --set-active=other
fastboot reboot-bootloader
fastboot flash --slot=other bootloader bootloader-tokay-<ver>.img
fastboot --set-active=other
fastboot reboot-bootloader
fastboot flash radio radio-tokay-<ver>.img
fastboot reboot-bootloader

# 2. Flash the AVB custom key (REQUIRES unlocked bootloader)
fastboot erase avb_custom_key
fastboot flash avb_custom_key avb_pkmd.bin

# 3. Optional GrapheneOS hardening (tokay is in the list at generate-release.sh:61)
fastboot oem uart disable
fastboot erase fips
fastboot erase dpm_a
fastboot erase dpm_b

# 4. Flash the signed image set (fastboot -w wipes userdata)
fastboot -w --skip-reboot update image-tokay-<ver>.zip
fastboot reboot-bootloader

# 5. LOCK THE BOOTLOADER
fastboot flashing lock
#   → Device prompts on-screen to confirm. Press Vol-Up to confirm.
#   → Bootloader locks. Device reverts to verified-boot-enforced state.

# 6. Reboot — device boots the signed image with verified boot GREEN (if all signatures validate).
fastboot reboot
```

**`fastboot flashing lock` behavior** (verified at `system/core/fastboot/fastboot.cpp:566-575`): this is an OEM command forwarded to the bootloader. On Pixel 9, locking requires that the currently-booted vbmeta chain validates against either Google's key or the flashed `avb_custom_key`. If you flash your signed image + your avb_pkmd.bin BEFORE locking, the lock succeeds and the device boots green.

### 3b. Does locking REQUIRE the custom key to be flashed first?

**Yes, for a custom-key build.** Sequence matters:
1. If you lock WITHOUT flashing `avb_custom_key` and WITHOUT a Google-signed image: the bootloader falls back to Google's embedded key, your custom-signed vbmeta fails verification, and the device will not boot (red state / recovery).
2. If you flash `avb_custom_key` THEN lock THEN boot your signed image: the bootloader uses your custom key, verifies your vbmeta chain, boots green.

**The GrapheneOS factory flow** (`generate-factory-images-common.sh:226-232`) flashes `avb_custom_key` BEFORE the image update and BEFORE any lock. The lock step itself is NOT in `flash-all.sh` — GrapheneOS expects the user to lock manually afterward (the official install guide walks the user through `fastboot flashing lock` after the factory flash). This is the correct order: unlock → flash key → flash image → lock.

### 3c. UX — what the user sees

On Pixel 9 with a custom-key-locked bootloader:
- **Green state** (`ro.boot.verifiedbootstate=green`): AVB chain validates against the custom key, bootloader locked. This is the desired steady state. The Pixel bootloader shows a brief "green" verified-boot indicator on cold boot (the standard Android verified-boot screen). GrapheneOS removes the yellow/orange warning screens for release-key builds — GuardTalkOS inherits this if built `user` (not `userdebug`) and signed with release keys. The current `tokay-cur-userdebug` target would show `yellow` (self-signed) because userdebug sets `ro.debuggable=1`; for production green state, build `tokay-cur-user`.
- **Yellow state** (`verifiedbootstate=yellow`): custom key, locked, but `ro.debuggable=1` or userdebug. AVB verifies but the OS is debuggable.
- **Orange state** (`verifiedbootstate=orange`): bootloader unlocked. This is the current dev state.
- **Red state** (`verifiedbootstate=red`): AVB verification FAILED. Device shows a "Your device is corrupt" warning and refuses to boot the OS without user confirmation each boot.

The verifiedbootstate prop is surfaced via `ro.boot.verifiedbootstate` (defined at `frameworks/base/services/core/java/com/android/server/pdb/PersistentDataBlockService.java:190`), and the device-state (locked/unlocked) via `ro.boot.vbmeta.device_state` (line 189).

The `KM_TAG_ROOT_OF_TRUST` (tag 704, line 87) is hardware-enforced (in the `HW_ENFORCED` sequence, line 329-330) and contains:
- `verifiedBootKey` — the hash of the verified boot key. With a custom AVB key, this is the hash of YOUR `avb_pkmd.bin`, NOT Google's. Apps/services that compare this to Google's known value will see a mismatch.
- `verifiedBootLocked` — true (bootloader locked).
- `verifiedBootState` — `VERIFIED` (0) if green; `SELF_SIGNED` (1) if yellow.
- `verifiedBootHash` — hash of the boot image.

**Impact on apps:**
- Apps that check `ro.boot.verifiedbootstate=green` (e.g., banking apps, some DRM): **UNAFFECTED** by a custom-key green-state lock. The prop reads `green`.
- Apps that perform hardware Keystore attestation and compare `verifiedBootKey` to Google's key (or to a server-side whitelist of manufacturer keys): **WILL FLAG the custom root of trust**. This is the same situation GrapheneOS faces — some apps refuse to run on GrapheneOS because its attestation shows a non-Google `verifiedBootKey`. GrapheneOS's solution is the `Auditor` app (paired-device attestation) and app developers updating their server-side whitelists.
- **StrongBox / hardware attestation:** the Titan M2 (Pixel 9) StrongBox attestation includes the verified-boot state. A custom-key-locked green-state device still attests `verifiedBootState=VERIFIED`; the only differentiator is `verifiedBootKey`. StrongBox itself is not compromised.

**`AttestationVerificationPeerDeviceVerifier`** (`frameworks/base/services/core/java/com/android/server/security/AttestationVerificationPeerDeviceVerifier.java:446-447`) explicitly requires `VERIFIED`:

```446:447:AttestationVerificationPeerDeviceVerifier.java
        if (attestationAttributes.getVerifiedBootState() != VERIFIED) {
            Slog.e(TAG, "Boot state not Verified.");
```

So the platform's own attestation-verification API passes for any green-state device (custom key or Google key). Only app-side server whitelists that hard-code Google's `verifiedBootKey` will reject.

## 4. Threat Model

### 4a. What tampering is BLOCKED by release signing + custom-key lock

| Threat | Blocked? | Mechanism | Evidence |
|---|---|---|---|
| Unsigned `boot.img` flashed via fastboot | ✅ | Bootloader rejects any boot.img whose AVB hash footer signature does not verify against the custom key (or Google's key if no custom key). | AVB hash-footer verification; `BOARD_AVB_BOOT_*` config |
| Modified `system.img` / `vendor.img` / `product.img` | ✅ | dm-verity hashtree in the AVB footer; the bootloader checks the root hash signed by the custom key. Any byte change fails verification → red state. | `BoardConfigPixelCommon.mk:7-19` (SHA-256 hashtree footers for system/vendor/product/system_ext/vendor_dlkm) |
| Rollback attack (older, vulnerable OS re-flashed) | ✅ (partial) | AVB rollback index (`BOARD_AVB_ROLLBACK_INDEX`, `BoardConfigMainlineCommon.mk:38`) — the bootloader stores the highest rollback index seen and refuses to boot images with a lower index. CAVEAT: the rollback index is per-partition and must be incremented deliberately in releases. | `build/make/target/board/BoardConfigMainlineCommon.mk:38` |
| `vendor` partition tampering | ✅ | vendor.img has its own AVB hashtree footer (chained via vbmeta_vendor). | `BoardConfigPixelCommon.mk:14` |
| `vbmeta` partition replacement (attacker flashes their own vbmeta signed by Google's test key) | ✅ | With custom-key lock + `avb_custom_key` flashed, the bootloader verifies vbmeta against YOUR key. A test-key-signed vbmeta fails. | AVB root-of-trust: bootloader uses `avb_custom_key` partition if present |
| Fastboot `flash` / `erase` / `-w` (userdata wipe) on a locked device | ✅ | Locked bootloader rejects all `fastboot flash` / `fastboot erase` commands except to unlock (which wipes userdata). | fastboot lock enforcement (bootloader-side) |
| Raw partition read of userdata via fastboot | ✅ (ciphertext) | Userdata is FBE (File-Based Encryption) encrypted; raw partition read yields ciphertext. Keys are in the Titan M2 / TEE, not on the partition. | AOSP FBE default; Pixel 9 uses FBE with hardware-wrapped keys |

### 4b. What is NOT blocked

| Threat | Why not |
|---|---|
| Evil-maid with physical access + your leaked AVB private key | If the attacker has your `avb.pem`, they can sign a malicious image, unlock (if OEM Unlocking is on), flash, and re-lock. The custom key does not protect against key compromise. Custody is the only defense. |
| TEE / StrongBox (Titan M2) compromise | AVB verifies the boot chain up to the OS; it does not protect against a TEE firmware exploit. Hardware attestation would surface this only if the TEE itself is not compromised. |
| Kernel exploit post-boot | AVB verifies integrity at boot; once the OS is running, a kernel exploit can modify the running system. AVB does not provide runtime integrity. |
| Bootloader vulnerability (e.g., buffer overflow in fastboot handling) | A bootloader bug could allow bypassing the lock check. Pixel bootloaders are updated via `bootloader.img` flashes (signed by Google — you cannot flash a custom bootloader). |
| `fastboot flashing unlock` by someone with physical access + OEM Unlocking enabled | Unlock wipes userdata but allows flashing any image. If OEM Unlocking is left on (the recovery path), this is an attack surface. Disable OEM Unlocking after lock for max security (at the cost of brick-on-key-loss). |

### 4c. Dependency on #3 (fastboot FS protection)

**Confirmed:** A locked bootloader (with or without custom key) rejects:
- `fastboot flash <any partition>` → "FAILED: device is locked" (or similar)
- `fastboot erase <any partition>` → rejected
- `fastboot -w` (userdata wipe) → rejected (only `fastboot flashing unlock` wipes, and that requires `get_unlock_ability=1`)

Userdata is FBE-encrypted, so even a raw partition dump (e.g., via a hardware flasher or a bootloader exploit that reads the userdata eMMC) yields ciphertext without the FBE keys (which live in the Titan M2 / TEE, hardware-wrapped). This is the A-FASTBOOT-PROT-RESEARCH FS-protection half: locking closes the fastboot FS door, FBE closes the raw-read door. Together with release signing + custom AVB key, the full verified-boot + encryption stack is enforced.

## 5. Go / No-Go Recommendation

### 5a. Verdict: **GO**

Release signing + custom-AVB-key + bootloader locking is GO for GuardTalkOS, with the following conditions:

1. **Key custody MUST be solved first.** The AVB private key (`avb.pem`) loss is a permanent brick. Recommend: generate fresh GuardTalkOS-owned keys, encrypt with scrypt, store 3 offline encrypted backups. Do NOT reuse the inherited GrapheneOS keys at `keys/tokay/` unless their provenance is fully trusted.
2. **Build target must be `user` not `userdebug`** for production green-state. The current `tokay-cur-userdebug` will boot yellow (self-signed) even with a custom-key lock because `ro.debuggable=1`. Switch to `tokay-cur-user` for release builds.
3. **Decide OEM Unlocking policy** before locking: leave enabled (recovery path, physical-access risk) or disable (no recovery, max security). Recommend: enabled until custody is proven, then disable per-device.

### 5b. Minimum Viable Path (MVP)

```
(a) Generate fresh keys (10 package keys via make_key + 1 AVB key via openssl genrsa)
    on an offline machine. Encrypt with a strong passphrase.
(b) Extract avb_pkmd.bin: avbtool extract_public_key --key avb.pem --output avb_pkmd.bin
(c) Build user target: lunch tokay-cur-user && m -j$(nproc) dist
(d) Sign: invoke generate-release.sh pattern (sign_target_files_apks -o -d <keys>
    --avb_vbmeta_key <avb.pem> --avb_vbmeta_algorithm SHA256_RSA4096 ... )
    → signed target-files → OTA + factory image.
(e) On device: enable OEM Unlocking, unlock bootloader.
(f) Flash avb_custom_key: fastboot erase avb_custom_key && fastboot flash avb_custom_key avb_pkmd.bin
(g) Flash signed factory image (flash-all.sh pattern).
(h) Lock bootloader: fastboot flashing lock  (confirm on-device).
(i) Verify: getprop ro.boot.verifiedbootstate  → green
            getprop ro.boot.vbmeta.device_state → locked
(j) Negative test: attempt to flash an unsigned boot.img → expect rejection.
```

### 5c. Risks / Trade-offs

| Risk | Mitigation |
|---|---|
| **Permanent brick on AVB key loss** | 3 offline encrypted backups; document the custody procedure; consider an HSM. |
| **Attestation/UX impact** | Apps that hard-code Google's `verifiedBootKey` will reject (same as GrapheneOS). Use the Auditor app pattern for paired attestation. Most apps checking `verifiedbootstate=green` are unaffected. |
| **Loss of fastboot dev convenience** | Reflashing requires `fastboot flashing unlock` (wipes userdata) or signed OTAs. Development must stay on a separate unlocked device. |
| **Rollback index management** | Must deliberately increment `BOARD_AVB_ROLLBACK_INDEX` for each release that needs to block downgrade. Forgetting this allows rollback attacks. |
| **`userdebug` vs `user`** | Production must be `user`. A `userdebug` custom-key-locked device boots yellow, weakening the verified-boot guarantee. |
| **Bootloader trust root** | The Pixel 9 bootloader trusts Google's embedded key OR the `avb_custom_key` partition. The bootloader itself is Google-signed (you cannot flash a custom bootloader). This is a trusted third party (Google) in the trust chain — acceptable, as it is the same model GrapheneOS uses. |

The `releases/2026061500/release-tokay-2026061500/script/` directory contains a complete, working signing pipeline (`generate-release.sh`, `decrypt-keys`, `generate-factory-images-common.sh`, `common.sh`). GuardTalkOS should:
