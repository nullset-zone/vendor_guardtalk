# GuardTalkOS Signing Key Runbook

> **Source of truth:** [`vendor/guardtalk/docs/SECURITY_SIGNING_REPORT.md`](../../docs/SECURITY_SIGNING_REPORT.md) (A-SIGN-RESEARCH #1, 2026-07-02)
>
> **Scope:** Offline key generation, encrypted backup, restoration, and
> bootloader locking for GuardTalkOS release builds on Pixel 9 (`tokay`).
>
> **Law 4 (Security First):** The keys generated by this runbook are the
> root of trust for every GuardTalkOS-locked device. **Loss of `avb.pem`
> after the bootloader is locked is a PERMANENT BRICK.** Read the warning
> in §6 before proceeding.

---

## 1. Prerequisites

### 1a. Offline machine (REQUIRED)

A dedicated, air-gapped machine:

- **No network** (Ethernet unplugged, Wi-Fi off).
- **No Bluetooth** (BT is excised from GuardTalkOS anyway; the signing
  host should have its BT radio disabled or removed).
- **No persistent plaintext keys.** Plaintext keys exist only in tmpfs
  (`/dev/shm`) during signing and are shredded on exit.
- A TTY or terminal (the key-generation scripts are interactive — they
  prompt for passphrases).
- Sufficient disk for the AOSP tree checkout (used only to locate
  `make_key` and `avbtool` — the full build does NOT need to run on this
  machine).

### 1b. Software

| Tool | Purpose | AOSP path |
|------|---------|-----------|
| `openssl` | RSA key generation, cert signing | system |
| `python3` | `avbtool` runtime | system |
| `gpg` | Encrypted backups (AES-256 symmetric) | system |
| `tar` | Archive creation | system |
| `shred` | Secure plaintext deletion | system |
| `make_key` | Package key (PKCS#8 + x509 PEM) generation | `development/tools/make_key` |
| `avbtool` | AVB public-key blob extraction | `external/avb/avbtool.py` |

Set `ANDROID_BUILD_TOP` to the root of the AOSP/GrapheneOS checkout on
the offline machine so the scripts can auto-locate `make_key` and
`avbtool`:

```bash
export ANDROID_BUILD_TOP=/path/to/aosp-checkout
```

### 1c. Verify the tooling scripts

Before trusting these scripts, review them in-tree:

```bash
# Syntax check (no execution, no keys generated)
bash -n vendor/guardtalk/scripts/generate-signing-keys.sh
bash -n vendor/guardtalk/scripts/backup-signing-keys.sh

# Confirm NO actual keys are committed in-tree
find vendor/guardtalk/ -name '*.pem' -o -name '*.pk8' -o -name '*.x509.pem' \
    2>/dev/null | grep -v '.bak' | head
# Expected: (no output)
```

## 2. Key Generation Procedure

### 2a. Run the generator

On the **offline machine**, from the AOSP checkout root:

```bash
export ANDROID_BUILD_TOP="$PWD"

# Decide where keys will live. This MUST be a persistent path on the
# offline machine (NOT tmpfs — keys must survive reboots for signing).
KEY_DIR=/mnt/secure/keys/guardtalk

vendor/guardtalk/scripts/generate-signing-keys.sh \
    --output-dir "$KEY_DIR"
```

The script will:

1. Locate `make_key` and `avbtool` (via `ANDROID_BUILD_TOP` or
   `--make-key` / `--avbtool`).
2. Print the **PERMANENT BRICK WARNING**.
3. Prompt for a passphrase for each of the 9 package keys (scrypt-encrypted
   PKCS#8). Use a strong passphrase. The same passphrase may be used for
   all 9 package keys, or distinct ones — operator choice.
4. Generate `avb.pem` (RSA-4096, unencrypted PEM — protected by `0600`
   permissions and the encrypted backup).
5. Extract `avb_pkmd.bin` (the public-key blob flashed to
   `avb_custom_key`).
6. Set `chmod 0600` on all private key material, `0700` on the directory.
7. Print a summary table.

### 2b. What is generated

| Key | Files | Algorithm | Purpose |
|-----|-------|-----------|---------|
| `releasekey` | `.pk8` + `.x509.pem` | RSA-4096 | OTA package signing |
| `platform` | `.pk8` + `.x509.pem` | RSA-4096 | Platform apps |
| `shared` | `.pk8` + `.x509.pem` | RSA-4096 | Shared-user apps |
| `media` | `.pk8` + `.x509.pem` | RSA-4096 | Media apps |
| `networkstack` | `.pk8` + `.x509.pem` | RSA-4096 | Network stack |
| `bluetooth` | `.pk8` + `.x509.pem` | RSA-4096 | BT stack |
| `nfc` | `.pk8` + `.x509.pem` | RSA-4096 | NFC stack |
| `sdk_sandbox` | `.pk8` + `.x509.pem` | RSA-4096 | SDK sandbox |
| `gmscompat_lib` | `.pk8` + `.x509.pem` | RSA-4096 | GMS compat |
| AVB | `avb.pem` | RSA-4096, `SHA256_RSA4096` | Root vbmeta signing |
| AVB public | `avb_pkmd.bin` | — | Bootloader `avb_custom_key` partition |

This matches the report §1a exactly (9 package keys + 1 AVB key, verified
against `releases/.../script/common.sh:136-146` and
`build/make/tools/releasetools/sign_target_files_apks.py:1437-1448`).

### 2c. Idempotency / re-runs

The script refuses to overwrite existing keys. To regenerate (e.g. for
key rotation, §7), back up the existing keys first, then:

```bash
vendor/guardtalk/scripts/generate-signing-keys.sh \
    --output-dir "$KEY_DIR" --force
```

## 3. Backup Procedure

**Create 3 encrypted backups in 3 geographically separate offline
locations.** This is the single most important custody control.

### 3a. Create a backup

```bash
KEY_DIR=/mnt/secure/keys/guardtalk
BACKUP_DIR=/mnt/secure/backups

vendor/guardtalk/scripts/backup-signing-keys.sh \
    --key-dir "$KEY_DIR" \
    --backup-dir "$BACKUP_DIR"
```

The script will:

1. Compute SHA-256 checksums of every source file.
2. Create a `tar.gz` of the key directory in tmpfs.
3. Encrypt it with `gpg --symmetric` (AES-256), prompting for a
   passphrase (or read from `--passphrase-file /dev/shm/passphrase.txt`).
4. **Verify** the backup by decrypting it and comparing checksums.
5. Shred all plaintext temp files.
6. Print the backup path + SHA-256 + the brick warning.

Output: `$BACKUP_DIR/guardtalk-signing-keys-<timestamp>.tar.gz.gpg`

### 3b. Repeat for 3 copies

Run §3a three times (or copy the resulting `.gpg` file to 3 separate
media). Store each copy in a different geographical location (e.g. 3
safes in 3 buildings/cities). The passphrase should be the same across
all 3 copies (you need to be able to restore) — store the passphrase
**separately** from the backup media, under separate physical custody
(e.g. a sealed envelope in a 4th safe, or split via Shamir's Secret
Sharing across 3 custodians).

### 3c. Test restoration from ONE backup

Before trusting any backup, restore it to a fresh tmpfs and verify the
keys match (§4). Do this immediately after generation, and again
periodically (at least annually) to detect media degradation.

---

## 4. Restoration Procedure

To restore keys from a backup (e.g. on a new signing host or after
media failure):

```bash
# 1. Create a tmpfs work area (NEVER restore to persistent disk plaintext)
RESTORE_DIR=$(mktemp -d /dev/shm/restore.XXXXXX)
chmod 0700 "$RESTORE_DIR"

# 2. Decrypt + extract the backup into tmpfs
gpg --decrypt --pinentry-mode loopback \
    /path/to/guardtalk-signing-keys-<timestamp>.tar.gz.gpg \
    | tar xzf - -C "$RESTORE_DIR"

# 3. Verify the restored key set
ls -la "$RESTORE_DIR"
sha256sum "$RESTORE_DIR"/*

# 4. If restoring for a signing operation, point the signing script at
#    the tmpfs path. If restoring for long-term custody, re-run
#    backup-signing-keys.sh to create a NEW backup of the restored keys
#    (do NOT leave plaintext on persistent disk).

# 5. When done, shred all plaintext
find "$RESTORE_DIR" -type f -exec shred -u {} +
rmdir "$RESTORE_DIR"
```

The `backup-signing-keys.sh` script already performs this
decrypt-and-verify cycle as its verification step, so a passing backup
run is itself proof that restoration works.

## 5. Bootloader Lock Procedure

> ⚠️ **Read §6 first.** Locking the bootloader with a custom AVB key is
> irreversible without the key.

This is the sequence from the report §3a, derived from the GrapheneOS
factory `flash-all.sh` template
(`releases/.../device/common/generate-factory-images-common.sh:226-232`)
and the fastboot command surface in `system/core/fastboot/fastboot.cpp:570-575`.

### 5a. Prerequisites (device side)

1. **Build target must be `user`, not `userdebug`.** A `userdebug`
   custom-key-locked device still reports `yellow`, but `userdebug`
   sets `ro.debuggable=1` which weakens the security posture. For the
   secure production state, build `tokay-cur-user`:
   ```bash
   lunch tokay-cur-user
   m -j$(nproc) dist
   ```
2. **Signed images.** Sign the target-files with the generated keys
   using the `sign_target_files_apks` invocation documented in the
   report §2a (`generate-release.sh:74-171`). The signed factory image
   zip + `avb_pkmd.bin` are required.
3. **OEM Unlocking enabled** on the device (Settings → Developer
   Options → OEM Unlocking). This sets `flashing get_unlock_ability = 1`.

### 5b. The sequence

```bash
# 0. PREREQUISITE: OEM Unlocking enabled on device (sets get_unlock_ability=1)

# 1. Flash bootloader + radio (slot A and B)
fastboot flash --slot=other bootloader bootloader-tokay-<ver>.img
fastboot --set-active=other
fastboot reboot-bootloader
fastboot flash --slot=other bootloader bootloader-tokay-<ver>.img
fastboot --set-active=other
fastboot reboot-bootloader
fastboot flash radio radio-tokay-<ver>.img
fastboot reboot-bootloader

# 2. Flash the AVB custom key (REQUIRES unlocked bootloader)
fastboot erase avb_custom_key
fastboot flash avb_custom_key avb_pkmd.bin

# 3. Optional GrapheneOS hardening (tokay is supported per generate-release.sh:61)
fastboot oem uart disable
fastboot erase fips
fastboot erase dpm_a
fastboot erase dpm_b

# 4. Flash the signed image set (fastboot -w wipes userdata)
fastboot -w --skip-reboot update image-tokay-<ver>.zip
fastboot reboot-bootloader

# 5. LOCK THE BOOTLOADER
fastboot flashing lock
#   → Device prompts on-screen to confirm. Press Vol-Up to confirm.
#   → Bootloader locks. Device reverts to verified-boot-enforced state.

# 6. Reboot — device boots the signed image with verified boot GREEN
#    (if all signatures validate and target is `user` not `userdebug`).
fastboot reboot
```

### 5c. Verify verified-boot state

After boot:

```bash
adb shell getprop ro.boot.verifiedbootstate
# Expected: yellow   (locked + custom AVB key — GuardTalkOS target state)

adb shell getprop ro.boot.vbmeta.device_state
# Expected: locked
```

States (per Android Verified Boot semantics; see also §11e):

| State | `verifiedbootstate` | Meaning |
|-------|---------------------|---------|
| Green | `green` | Locked + **OEM-embedded** AVB key (Google's key in the Pixel bootloader ROM). NOT expected for GuardTalkOS — would indicate the OEM key matched, not the GuardTalk custom key. |
| Yellow | `yellow` | Locked + **custom** AVB key (injected via `fastboot flash avb_custom_key`). **GuardTalkOS desired steady state.** |
| Orange | `orange` | Bootloader unlocked. (Dev state.) |
| Red | `red` | AVB verification FAILED — device shows "Your device is corrupt". |

> **Why `yellow` and not `green`?** `green` requires the AVB key match the
> OEM (Google) key baked into the Pixel bootloader ROM. GuardTalkOS uses
> its own offline-generated AVB key (injected via `avb_custom_key`), so a
> correctly-locked GuardTalkOS device reports `yellow`. `green` would be a
> security anomaly in our context. See §11e for the full script-enforced
> verification semantics.

### 5d. Negative test

```bash
# Attempt to flash an unsigned boot.img on the LOCKED device — expect rejection:
fastboot flash boot unsigned-boot.img
# Expected: FAILED: device is locked (or similar)
```

### 5e. Post-lock OEM Unlocking policy

Decide whether to leave OEM Unlocking enabled or disable it:

- **Leave enabled** → recovery path on key loss (unlock + reflash),
  at the cost of physical-access attack surface.
- **Disable** → no recovery on key loss (max security).

**Recommendation (per report §3a):** leave OEM Unlocking enabled until
custody is proven (3 backups verified), then disable per-device for
maximum security.

## 6. PERMANENT BRICK WARNING

> ### ⚠️ LOSS OF `avb.pem` AFTER BOOTLOADER LOCK = PERMANENT BRICK ⚠️
>
> There is **NO recovery path** without the AVB private key.

Once the bootloader is locked with your custom AVB key flashed to
`avb_custom_key`:

1. The bootloader will **only** boot images whose vbmeta chain is signed
   by **your** `avb.pem`.
2. To reflash, you must either:
   - Unlock the bootloader (`fastboot flashing unlock`), which **wipes
     userdata** and requires `get_unlock_ability=1`. **If OEM Unlocking
     was disabled after lock (the secure default), the device CANNOT be
     unlocked.**
   - Re-sign images with the AVB key — **impossible if the key is lost.**
3. A lost `avb.pem` with OEM Unlocking disabled = **PERMANENT BRICK**.
   No image can be signed, no unlock is possible, the device will never
   boot again.

**This is why §3 (3 encrypted backups in 3 locations) is mandatory
before §5 (lock).** Custody is the **only** defense against key loss.

## 7. Key Rotation Procedure

Key rotation replaces the GuardTalkOS signing key set. It is required
if any key is suspected compromised, or periodically as policy.

### 7a. Rotation requires an UNLOCKED bootloader

Because locking with a new AVB key requires flashing a new
`avb_custom_key`, rotation requires the bootloader to be unlocked first:

```bash
# 1. Ensure OEM Unlocking is enabled (Settings → Developer Options)
# 2. Unlock (WIPES USERDATA):
fastboot flashing unlock
# 3. Confirm on-device (Vol-Up)
```

### 7b. Generate the new key set

On the offline machine, run §2 with a **new** `--output-dir` (do not
overwrite the old keys — keep them for forensic/rollback purposes until
the new set is proven):

```bash
vendor/guardtalk/scripts/generate-signing-keys.sh \
    --output-dir /mnt/secure/keys/guardtalk-2026XXXX
```

### 7c. Back up the new key set

Run §3 for the new key set. **3 new backups.**

### 7d. Re-sign and re-flash

Build a new signed factory image with the new keys (report §2a), then
run §5b (flash new `avb_custom_key` + signed image + lock).

### 7e. Securely destroy the old key set

Once the new key set is proven (devices boot yellow, OTA verifies), shred
the old private keys:

```bash
find /mnt/secure/keys/guardtalk-old -type f -exec shred -u {} +
rmdir /mnt/secure/keys/guardtalk-old
```

> **Rollback index note (report §4a):** `BOARD_AVB_ROLLBACK_INDEX`
> (`build/make/target/board/BoardConfigMainlineCommon.mk:38`) must be
> incremented deliberately for each release that needs to block
> downgrade. Forgetting this allows rollback attacks even after
> rotation.

## 8. What NOT to Do

| ❌ Do NOT | Why |
|----------|-----|
| **Commit keys to git.** | The `.gitignore` must cover `keys/`. Keys in git = permanent leak. The scripts in `vendor/guardtalk/scripts/` are tooling ONLY; they produce no keys when committed. |
| **Put keys on a networked machine.** | Network exposure = exfiltration risk. Keys live ONLY on the offline signing host + encrypted backups. |
| **Leave plaintext keys on persistent disk.** | Plaintext keys exist only in tmpfs (`/dev/shm`) during signing. The `trap` in `generate-release.sh:18-21` and in `backup-signing-keys.sh` ensures shredding. |
| **Reuse the inherited `keys/tokay/` GrapheneOS keys.** | Any GrapheneOS-signed image would also pass AVB on a GuardTalkOS-locked device, defeating the GuardTalkOS-specific root of trust (report §1c). |
| **Lock the bootloader before verifying backups.** | If `avb.pem` is lost and no working backup exists, the device is bricked (§6). Verify 3 backups BEFORE locking. |
| **Build `userdebug` for production.** | A `userdebug` custom-key-locked device still reports `yellow` (locked + custom key), but `ro.debuggable=1` weakens the security posture. Production must be `tokay-cur-user` (report §5b, §5c). |
| **Disable OEM Unlocking before custody is proven.** | Disabling OEM Unlocking removes the only recovery path. Disable only after 3 verified backups exist (report §3a). |
| **Pass passphrases on the command line.** | Leaks via `ps(1)`, shell history, and audit logs. Use `--passphrase-file /dev/shm/...` or the interactive prompt (report §1c). |
| **Skip the backup verification step.** | An unverified backup may be corrupt or have a wrong passphrase. `backup-signing-keys.sh` verifies by decrypt + SHA-256 compare; never skip this. |
| **Access `doctrine/` or `governance/laws\|gates/`.** | Forbidden by the AEGIS framework — doctrine is immutable and not AI-modifiable. |

## 10. Signing a Release Build

> **Phase 2 deliverable (T-SIGN-PIPELINE).** This section covers the
> operator-run signing pipeline that consumes the keys from §2 plus the
> unsigned `m dist` artifacts and produces a signed, lockable release
> bundle. The script is `vendor/guardtalk/scripts/sign-build.sh`.

### 10a. Prerequisites

1. **Keys on the build server.** T-SIGN-KEYGEN must be complete: the
   11 key files (`avb.pem`, `avb_pkmd.bin`, and 9 package
   `.pk8` + `.x509.pem` pairs) live at a known path, e.g.
   `/home/openstatestack/guardtalk-keys/guardtalk/`. The script
   validates their presence and hard-errors if any are missing.
2. **AOSP/GrapheneOS checkout** with `m dist` already run for the
   target device:
   ```bash
   lunch tokay-cur-user        # MUST be user, not userdebug (§5a)
   m -j$(nproc) dist
   ```
   This produces, under `releases/<BUILD_NUMBER>/`:
   - `tokay-target_files.zip` (unsigned target-files)
   - `tokay-otatools.zip` (releasetools binaries)
3. **Build tools in PATH.** `openssl`, `unzip`, `sha256sum`, `shred`
   are all standard build-env tools. `fastboot` is only needed for the
   optional `optimize-factory-image` step.
4. **Passphrase** for the encrypted `.pk8` keys (set during §2). Have
   it ready, or export it as `GUARDTALK_KEY_PASSPHRASE` and pass
   `--passphrase-env`.

### 10b. Invocation

From the AOSP checkout root (`/mnt/Big-Storage/GuardTalk/GrapheneOS-worktree`):

```bash
vendor/guardtalk/scripts/sign-build.sh \
    --key-dir     /home/openstatestack/guardtalk-keys/guardtalk \
    --device      tokay \
    --build-dir   "$PWD" \
    --release-out releases/<BUILD_NUMBER> \
    --passphrase-env     # if $GUARDTALK_KEY_PASSPHRASE is set
```

### 10c. What the script does

1. **Validates** the 11 key files in `--key-dir` (hard-error on any
   missing).
2. **Decrypts keys to tmpfs** (`/dev/shm/gt-sign.XXXXXX`), replicating
   `script/decrypt-keys`: reads the passphrase into env var `password`,
   loops over the 9 `.pk8` keys doing
   `openssl pkcs8 -topk8 -inform DER -outform DER -nocrypt`, and
   handles `avb.pem` separately (PEM, not DER). A `trap` shreds every
   file in the tmpfs dir on exit (Law 4).
3. **Unpacks `tokay-otatools.zip`** into a workdir and prepends its
   `bin/` to `PATH` so `sign_target_files_apks`,
   `ota_from_target_files`, and `img_from_target_files` resolve.
4. **Runs `sign_target_files_apks`** with the FULL `--extra_apks` /
   `--extra_apex_payload_key` flag list, **copied verbatim from
   `script/generate-release.sh:74-171`**. A missing or paraphrased
   apex entry causes AVB to reject the signature — do not edit the
   list.
5. **Generates the OTA update zip** via `ota_from_target_files -k
   <key-dir>/releasekey`.
6. **Generates the factory image zip** via
   `img_from_target_files`, then sources
   `device/common/generate-factory-images-common.sh` (with the env
   block from `generate-release.sh:43-66`) to produce the factory
   bundle.
7. **Optionally optimizes** the factory image with
   `fastboot -S 0xf900000 optimize-factory-image` (tokay's
   `MAX_DOWNLOAD_SIZE`).
8. **Writes `signed/MANIFEST.txt`** listing every output zip with its
   SHA-256, the SHA-256 of each `.x509.pem` (key fingerprints), and
   the SHA-256 of `avb_pkmd.bin` (Law 10 — Audit Trail).

All outputs land in `<release-out>/signed/`.

### 10d. MANIFEST.txt format

```
GuardTalkOS Signed Release Manifest
===================================
Generated : 2026-07-03T03:14:15Z
Device    : tokay
...
── Output files ──────────────────────────────────────────────────
  tokay-target_files-signed.zip            <sha256>
  tokay-ota_update-<BUILD>.zip             <sha256>
  tokay-img-<BUILD>.zip                    <sha256>
  tokay-factory-<BUILD>.zip                <sha256>
── Key fingerprints (SHA-256 of each .x509.pem) ─────────────────
  releasekey          <sha256>
  platform            <sha256>
  ...
── AVB public-key blob ───────────────────────────────────────────
  avb_pkmd.bin        <sha256>
```

### 10e. Reversibility / rollback

If a signing run produces a broken bundle, simply re-run the script
with a fresh `--release-out`. The unsigned target-files zip is never
modified; signing is a pure function of (target-files, keys). To roll
back to a previous signed release, point `--release-out` at the
previous build's directory.

## 11. Flashing & Locking a Device

> **Phase 2 deliverable (T-SIGN-PIPELINE).** Covers the operator-run
> flashing + locking + verification flow. The script is
> `vendor/guardtalk/scripts/flash-signed.sh`.

### 11a. Prerequisites

1. **A signed release bundle** from §10 (`<release-out>/signed/`),
   containing `tokay-factory-<BUILD>.zip` (or `tokay-img-<BUILD>.zip`)
   and `avb_pkmd.bin`.
2. **Device in fastboot mode** (power off, hold Volume-Down + Power,
   or `adb reboot bootloader`).
3. **OEM Unlocking enabled** on the device (Settings → Developer
   Options → OEM Unlocking). This sets `flashing get_unlock_ability=1`.
   The script will refuse to proceed if this is 0.
4. **Battery ≥ 30%.** The script warns if `battery-soc-ok != yes`.
5. **3 verified key backups exist (§3).** Locking is irreversible
   without `avb.pem` — see §6.

### 11b. Invocation

```bash
vendor/guardtalk/scripts/flash-signed.sh \
    --release-dir releases/<BUILD_NUMBER>/signed \
    --device tokay \
    --wipe-userdata       # acknowledge the unlock wipe
    # --no-lock           # bring-up mode: flash but skip lock
    # --yes               # non-interactive
```

### 11c. The avb_custom_key dance (BEFORE first flash)

The script performs, before any image flash:

1. `fastboot flashing get_unlock_ability` — must be `1`.
2. `fastboot getvar unlocked` — if `no`, the device must be unlocked
   first (this **wipes userdata** — the script prompts for
   confirmation, or pass `--wipe-userdata`).
3. `fastboot erase avb_custom_key` — clear any prior custom key.
4. `fastboot flash avb_custom_key <release-dir>/avb_pkmd.bin` —
   inject the GuardTalk AVB public key.

Only after the custom key is flashed does the script flash the signed
factory image (`fastboot update tokay-factory-<BUILD>.zip`).

### 11d. The irreversible `flashing lock`

After flashing, the script:

1. `fastboot reboot-bootloader`
2. Prints the **PERMANENT BRICK WARNING** (§6) and prompts for
   confirmation (or `--yes`).
3. `fastboot flashing lock` — the device prompts on-screen; press
   Vol-Up to confirm. The bootloader locks to the GuardTalk AVB key.
4. `fastboot reboot` — device boots the signed image.

> ⚠️ **Once locked, the device will ONLY boot images signed by your
> `avb.pem`.** Loss of `avb.pem` with OEM Unlocking disabled =
> **PERMANENT BRICK** (§6). Verify 3 backups before locking.

### 11e. Verification table (mandatory)

After boot, the script verifies (via `adb shell getprop`):

| Property | Required | Meaning |
|----------|----------|---------|
| `ro.boot.verifiedbootstate` | `yellow` | Locked + custom AVB key (GuardTalk key injected via `avb_custom_key`). This is the **target state** for GuardTalkOS. |
| `ro.boot.flash.locked` | `1` | Bootloader is locked. |
| `ro.product.name` | `tokay` (or `tokay_cur`) | Correct device. |

#### Verified-boot state semantics (Android Verified Boot)

GuardTalkOS uses its **own** offline-generated AVB key, injected via
`fastboot flash avb_custom_key`. This means a correctly-locked GuardTalkOS
device reports **`yellow`**, NOT `green`. This is the CORRECT, EXPECTED, and
SECURE state.

| State | `verifiedbootstate` | Meaning | Script action |
|-------|---------------------|---------|---------------|
| Green | `green` | Locked + **OEM-embedded** AVB key (Google's key in the Pixel bootloader ROM). NOT achievable for GuardTalkOS — would indicate the OEM key matched, not the GuardTalk key. | ⚠ WARNING (still PASS — device is locked+verified, but the key is unexpected; investigate `avb_custom_key`). |
| Yellow | `yellow` | Locked + **custom** AVB key (injected via `fastboot flash avb_custom_key`). **GuardTalkOS target state.** | ✓ PASS |
| Orange | `orange` | Bootloader unlocked. | ✗ FAIL |
| Red | `red` | Locked, but AVB verification FAILED — image rejected by the bootloader. | ✗ FAIL |

> **Why not `green`?** `green` requires the AVB key match the
> OS-embedded (OEM/Google) key baked into the Pixel bootloader ROM.
> GuardTalkOS does not have Google's key and uses its own instead, so
> `green` would be a security anomaly (it would suggest the GuardTalk
> custom key was NOT actually flashed, or the OEM key matched by
> mistake). The `yellow` state is what a correctly-locked
> custom-AVB-key device reports, and `fastbootd`'s `GetDeviceLockStatus()`
> correctly treats `yellow` as locked (anything ≠ `orange` is locked —
> see `SECURITY_FASTBOOT_PROT_REPORT.md` §1.1, §4.1).

If any mandatory check fails (`orange`, `red`, `flash.locked != 1`, or
product mismatch), the script prints a diagnostic table and exits
non-zero. A `green` warning does not fail the script but prints a
diagnostic for operator investigation.

### 11f. Fastboot-FS-protection spot-check

Per `SECURITY_FASTBOOT_PROT_REPORT.md` §4 / §8, after a successful
lock the script reboots to the bootloader and asserts that:

1. **`fastboot fetch vendor_boot` is rejected** — on a locked device
   (or any `user` build), `fetch` must FAIL
   (`commands.cpp:753-758`, `Android.bp:145-148`).
2. **`fastboot flash system <unsigned.img>` is rejected** — AVB
   verification must fail
   (`commands.cpp:606-608`; bootloader-level rejection).

The script then reboots the device back to the OS so it is not left
in a broken state.

### 11g. Rollback path (re-unlock)

If a device must be recovered (e.g. to re-flash with a different key
set during §7 rotation):

```bash
# 1. Ensure OEM Unlocking is enabled (Settings → Developer Options).
#    If OEM Unlocking was DISABLED after lock (§5e secure default),
#    the device CANNOT be unlocked — it is a permanent brick without
#    the AVB key. There is no recovery path.
# 2. Unlock (WIPES USERDATA):
fastboot flashing unlock
# 3. Confirm on-device (Vol-Up).
# 4. The device is now unlocked (verifiedbootstate=orange). Re-flash
#    via flash-signed.sh with the new signed release + new avb_pkmd.bin.
```

> **`--no-lock` bring-up mode:** for first-time bring-up, pass
> `--no-lock` to flash the signed image and verify it boots, without
> committing to the irreversible lock. Re-run without `--no-lock`
> once the image is proven.
